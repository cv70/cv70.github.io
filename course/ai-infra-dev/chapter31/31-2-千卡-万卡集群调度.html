31.2 千卡/万卡集群调度

超大规模集群的资源管理与调度策略

大规模集群调度挑战

千卡/万卡级集群的调度系统面临资源规模大、任务类型多样、通信拓扑复杂、故障率高等挑战。传统的调度系统无法满足LLM训练对资源亲和性和低延迟通信的需求。

⚙️ 调度系统架构

Slurm架构

Slurm组件：
├── slurmctld：中央控制器
├── slurmd：节点守护进程
├── slurmdbd：数据库守护进程
├── slurmrestd：REST API服务
└── sacctmgr：管理工具
  • 成熟稳定，广泛应用
  • 支持GRES（通用资源调度）
  • 作业脚本灵活
  • 丰富的调度策略

Volcano架构

Volcano组件：
├── volcano-controller：调度控制器
├── volcano-admission：准入控制
├── volcano-scheduler：调度器
└── volcano-agent：节点代理
  • 基于Kubernetes
  • 原生支持批处理
  • Gang Scheduling支持
  • 公平调度与优先级

🎛️ Gang Scheduling（组调度）

分布式训练调度核心机制

Gang Scheduling确保分布式训练的所有Pod/任务同时启动或同时失败，避免部分资源就绪导致的任务卡死。 

Slurm Gang Scheduling配置：
# salloc配置示例
#!/bin/bash
#SBATCH --job-name=llm-training
#SBATCH --nodes=128
#SBATCH --ntasks-per-node=8
#SBATCH --gres=gpu:8
#SBATCH --exclusive
#SBATCH --time=7-00:00:00

Volcano PodGroup示例：
apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: llm-training
spec:
  minMember: 1024
  minResources:
    nvidia.com/gpu: "1024"
  queue: training

🔄 资源亲和性调度

亲和性类型 作用 配置方式 适用场景
节点亲和性 任务分配到指定节点 --nodelist 指定硬件配置节点
拓扑亲和性 任务分配到相同机架 节点标签选择 减少跨机架通信
GPU亲和性 Pod绑定特定GPU NVIDIA GPU Operator MPS/VGPU场景
Pod亲和性 相关任务部署在一起 PodAffinity 同构任务调度
💡
调度优化技巧

对于张量并行任务，建议调度到NVLink连接的节点；对于数据并行任务，可以跨机架分布以均衡网络负载。根据并行策略选择合适的亲和性策略可以显著提升训练效率。

🚦 多租户资源隔离

资源配额

Slurm账户配置：
sacctmgr -i add account team1 \
  Organization=Team1 \
  Description="Team 1"

sacctmgr modify account team1 \
  set GrpTRES=cpu=2000,mem=4T,node=100,gpu=800

Volcano队列配置：
apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata:
  name: team1-queue
spec:
  weight: 10
  capability:
    cpu: "2000"
    memory: 4TGi
    nvidia.com/gpu: "800"

📊 优先级与抢占机制

任务优先级调度

Slurm优先级配置：
PriorityType=priority/multifactor
PriorityWeightFairshare=10000
PriorityWeightJobSize=1000
PriorityWeightQOS=10000
PriorityWeightPartition=1000

作业优先级设置：
#SBATCH --qos=high-priority
#SBATCH --nice=-100

抢占配置：
PreemptType=preempt/qos
PreemptMode=REQUEUE
PreemptExemptTime=00:05:00

优先级调度确保重要任务优先获得资源，抢占机制允许高优先级任务抢占低优先级任务的资源，需要配置合适的豁免时间避免任务频繁重启。

🔍 调度系统监控

监控指标 工具 关键阈值 告警建议
作业等待时间 squeue >2小时 调度策略优化
集群利用率 sinfo <80% 资源碎片化处理
任务失败率 sacct >5% 检查节点状态
调度延迟 调度器日志 >30秒 调度器扩容
⚠️
常见问题

大规模集群常出现资源碎片化问题。可以通过动态作业调整、资源重分配、弹性作业调度等策略缓解。定期进行资源整理和作业迁移也是必要的运维工作。

📈 调度性能优化

优化策略

  • 调度器并行化：使用多调度器分担压力
  • 增量调度：只调度变化的部分资源
  • 缓存优化：缓存节点状态减少查询
  • 批量调度：批量处理减少调度次数
  • 调度队列：按优先级队列处理
  • 预测调度：预测资源需求提前分配

🔧 实践配置示例

# Slurm大模型训练作业模板
#!/bin/bash
#SBATCH --job-name=gpt-training
#SBATCH --partition=ai-gpu
#SBATCH --nodes=256
#SBATCH --ntasks-per-node=8
#SBATCH --gres=gpu:8
#SBATCH --exclusive
#SBATCH --time=14-00:00:00
#SBATCH --qos=llm-training
#SBATCH --output=%j.out
#SBATCH --error=%j.err
#SBATCH --requeue
#SBATCH --open-mode=append

# 节点亲和性：选择相同交换机的节点
#SBATCH --switches=1@4-24:00:00

# 启动分布式训练
srun torchrun \
  --nnodes=256 \
  --nproc_per_node=8 \
  --rdzv_id=$SLURM_JOB_ID \
  --rdzv_backend=c10d \
  --rdzv_endpoint=$SLURM_NODELIST:29500 \
  train.py \
  --config configs/gpt-100b.yaml
