59.2 GraphQL vs REST

深入理解两种 API 设计范式的差异

📊 核心理念对比

REST

以资源为中心，每个资源有独立的 URL，通过 HTTP 方法表达操作。

// REST 设计思路 资源 -> URL 操作 -> HTTP 方法 /users GET // 获取列表 /users/123 GET // 获取单个 /users POST // 创建 /users/123 PUT // 更新 /users/123 DELETE // 删除

GraphQL

以图为中心，单一端点，客户端通过查询语言精确描述需求。

// GraphQL 设计思路 单一端点 -> /graphql 操作 -> Query/Mutation/Subscription query { user(id: 123) { name posts { title } } }

🔍 数据获取对比

场景：获取用户信息及其最近的文章

REST 方式

// 请求 1: 获取用户信息 GET /api/users/123 // 响应 (可能包含很多不需要的字段) { "id": 123, "name": "张三", "email": "zhang@example.com", "phone": "...", "address": "...", "bio": "...", "avatar": "..." // ...更多字段 } // 请求 2: 获取用户的文章 GET /api/users/123/posts?limit=5 // 问题：需要 2 次请求，第一次过度获取

GraphQL 方式

// 单次请求 query { user(id: 123) { name email posts(limit: 5) { title createdAt } } } // 响应 (精确返回所需字段) { "data": { "user": { "name": "张三", "email": "zhang@example.com", "posts": [ { "title": "文章1", "createdAt": "..." }, { "title": "文章2", "createdAt": "..." } ] } } } // 优点：1 次请求，精确字段

📋 功能对比表

特性 REST GraphQL
端点设计 多个 URL 端点 单一端点 /graphql
数据结构 服务器预定义 客户端动态指定
请求次数 关联数据需多次请求 一次请求获取所有数据
HTTP 缓存 原生支持（浏览器/CDN） 需要额外处理
类型系统 无内置（OpenAPI 可补充） 内置强类型 Schema
错误处理 HTTP 状态码 响应中的 errors 字段
版本管理 URL 版本号 /v1, /v2 演进式 Schema，无需版本
实时更新 需 WebSocket 单独实现 内置 Subscription
学习曲线 低，广泛熟悉 中等，需学习新概念
工具支持 Swagger、Postman GraphiQL、Apollo Studio

✅ GraphQL 的优势场景

移动应用

移动设备网络不稳定，GraphQL 减少请求次数，优化带宽使用。

  • 一次请求获取所有数据
  • 减少网络延迟
  • 节省流量

复杂关联数据

多个资源相互关联的场景，GraphQL 更高效。

  • 灵活的数据关联
  • 避免 N+1 请求
  • 按需加载数据

多端应用

Web、iOS、Android 需求不同，GraphQL 让各端按需获取。

  • 各端自定义字段
  • 统一 API 入口
  • 减少接口维护

快速迭代

前端需求变化频繁，GraphQL 减少后端改动。

  • 前端自主调整字段
  • 无需新增接口
  • 持续演进

✅ REST 的优势场景

简单 CRUD API

资源结构简单，操作直接，REST 更直观。

  • 易于理解和实现
  • 标准 HTTP 方法
  • 成熟生态

需要 HTTP 缓存

大量读操作、需要 CDN 缓存的场景，REST 原生支持。

  • 浏览器缓存
  • CDN 缓存
  • 代理缓存

团队熟悉度

团队对 REST 更熟悉，学习成本低。

  • 广泛认知
  • 文档丰富
  • 招聘容易

文件上传/二进制

文件上传等二进制操作，REST 更简单。

  • multipart/form-data
  • 流式上传
  • 浏览器原生支持

🔄 混合方案

实际项目中，可以同时使用 REST 和 GraphQL，各自处理擅长的场景。

// 混合 API 设计 // REST 处理简单资源和文件操作 POST /api/upload // 文件上传 GET /api/static/:file // 静态资源 GET /api/health // 健康检查 // GraphQL 处理复杂数据查询 POST /graphql // 数据查询和变更 // NestJS 实现 @Module({ imports: [ GraphQLModule.forRoot({...}), ], controllers: [ UploadController, // REST 控制器 HealthController, // REST 控制器 ], }) export class AppModule {}

📊 选择决策指南

因素 选择 REST 选择 GraphQL
数据关系 简单、扁平 复杂、多层级关联
客户端类型 单一客户端 多种客户端（Web/App/小程序）
缓存需求 强依赖 HTTP 缓存 实时数据为主
团队经验 熟悉 REST 愿意学习新技术
项目阶段 快速原型 长期演进项目
文件操作 大量文件上传 少量或无
💡
建议

不要为了使用新技术而选择 GraphQL。根据项目实际需求、团队情况和长期维护成本做出选择。GraphQL 不是 REST 的替代品，而是另一种选择。

📝 小结

  • REST 以资源为中心，GraphQL 以图为中心
  • GraphQL 解决过度获取和多次请求问题
  • REST 在缓存和简单场景更有优势
  • GraphQL 适合复杂关联数据和多端应用
  • 实际项目可以混合使用两种方案
  • 根据项目需求选择合适的技术方案
