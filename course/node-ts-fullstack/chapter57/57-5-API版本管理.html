57.5 API 版本管理

管理 API 演进，保持向后兼容性

📖 为什么需要版本管理

API 作为公共接口，需要随着业务发展不断演进。版本管理确保在不影响现有客户端的情况下，安全地引入新功能和改进。

💡
版本管理的目标
  • 保持向后兼容性，不破坏现有客户端
  • 支持多个版本并行运行
  • 清晰的生命周期管理
  • 便于 API 的演进和废弃

🔢 版本号规范

语义化版本号（SemVer）

语义化版本号格式：MAJOR.MINOR.PATCH

部分 说明 API 变更
MAJOR 主版本号 不兼容的 API 变更
MINOR 次版本号 向后兼容的功能新增
PATCH 修订号 向后兼容的问题修复
// 版本号示例 v1.0.0 // 初始版本 v1.1.0 // 新增功能，向后兼容 v1.1.1 // Bug 修复 v2.0.0 // 破坏性变更，新主版本

🔗 版本管理策略

1. URL 路径版本控制

最常用的方式，版本号直接嵌入 URL 路径中。

// API URL 示例 GET /api/v1/users GET /api/v2/users GET /api/v2/users/123 // 优点：清晰直观，易于缓存 // 缺点：URL 变化，需要更新客户端

2. 查询参数版本控制

通过查询参数指定版本。

// 查询参数示例 GET /api/users?version=1 GET /api/users?version=2 GET /api/users?v=2 // 优点：灵活，URL 不变 // 缺点：容易被忽略，缓存复杂

3. 请求头版本控制

通过自定义请求头指定版本。

// 自定义请求头 GET /api/users Accept-Version: 2 // 或使用 Accept 头 GET /api/users Accept: application/vnd.myapi.v2+json // 优点：URL 简洁，RESTful 风格 // 缺点：需要客户端配置请求头

4. 主机名版本控制

不同版本使用不同的子域名或主机名。

// 主机名版本控制 GET https://v1.api.example.com/users GET https://v2.api.example.com/users // 优点：完全隔离，便于独立部署 // 缺点：DNS 配置复杂

📊 版本策略对比

策略 优点 缺点 适用场景
URL 路径 直观、易缓存、易测试 URL 变化 公开 API、推荐使用
查询参数 灵活、URL 不变 易忽略、缓存复杂 简单场景
请求头 URL 简洁、RESTful 需配置头、调试不便 内部 API
主机名 完全隔离 配置复杂 大规模系统

💻 NestJS 版本控制实现

// main.ts - 启用版本控制 import { NestFactory } from '@nestjs/core'; import { VersioningType } from '@nestjs/common'; import { AppModule } from './app.module'; async function bootstrap() { const app = await NestFactory.create(AppModule); // 启用 URI 版本控制 app.enableVersioning({ type: VersioningType.URI, }); await app.listen(3000); } bootstrap(); // users.controller.v1.ts import { Controller, Get, Version } from '@nestjs/common'; @Controller({ path: 'users', version: '1', }) export class UsersControllerV1 { @Get() findAll() { return { version: 1, message: '用户列表 V1' }; } @Get(':id') @Version('2') // 单个路由使用不同版本 findOne() { return { version: 2, message: '用户详情 V2' }; } } // users.controller.v2.ts @Controller({ path: 'users', version: '2', }) export class UsersControllerV2 { @Get() findAll() { return { version: 2, data: [ { id: 1, name: '张三', role: 'admin' } ], meta: { total: 100 } }; } }

Header 版本控制

// main.ts - Header 版本控制 app.enableVersioning({ type: VersioningType.HEADER, header: 'X-API-Version', }); // 请求示例 GET /users HTTP/1.1 X-API-Version: 2

Media Type 版本控制

// main.ts - Media Type 版本控制 app.enableVersioning({ type: VersioningType.MEDIA_TYPE, key: 'v', }); // 请求示例 GET /users HTTP/1.1 Accept: application/vnd.myapi.v2+json

🔄 版本生命周期管理

阶段 1

发布（Release）

新版本发布，标记为 Current。同时维护旧版本。

阶段 2

维护（Maintenance）

旧版本进入维护模式，只修复关键 Bug 和安全问题。

阶段 3

弃用（Deprecated）

发布弃用公告，设置过期日期。响应头添加 Deprecation 警告。

阶段 4

下线（Sunset）

旧版本停止服务，返回 410 Gone 或重定向到新版本。

// 弃用响应头示例 HTTP/1.1 200 OK Deprecation: true Sunset: Sat, 31 Dec 2024 23:59:59 GMT Link: ; rel="successor-version" { "data": [...], "warning": "此 API 版本已弃用，请迁移到 v2" }

📋 版本迁移最佳实践

兼容性变更（不需要升级主版本）

  • 新增可选字段
  • 新增 API 端点
  • 新增可选参数
  • Bug 修复
  • 性能优化

破坏性变更（需要升级主版本）

  • 删除字段或端点
  • 重命名字段
  • 修改数据类型
  • 修改必需参数
  • 修改认证方式
⚠️
版本管理建议
  • 不要过早发布新版本，尽量通过非破坏性变更解决问题
  • 提供详细的迁移文档和变更日志
  • 给予足够的迁移时间（通常 6-12 个月）
  • 监控旧版本使用情况，通知活跃用户

📝 小结

  • API 版本管理确保 API 平稳演进
  • 语义化版本号清晰表达变更类型
  • URL 路径版本控制是最常用的方式
  • NestJS 内置支持多种版本控制策略
  • 建立完善的版本生命周期管理流程
