🔧 负载均衡方案

Nginx

  • 类型：反向代理负载均衡
  • 优点：成熟稳定，配置简单
  • 缺点：对GPU状态无感知
  • 适用：通用负载均衡

HAProxy

  • 类型：TCP/HTTP负载均衡
  • 优点：高性能，支持健康检查
  • 缺点：配置相对复杂
  • 适用：高性能场景

Traefik

  • 类型：云原生负载均衡
  • 优点：自动发现，K8s集成
  • 缺点：学习曲线较陡
  • 适用：微服务架构

Istio

  • 类型：服务网格负载均衡
  • 优点：细粒度控制，可观测性
  • 缺点：复杂度高，资源开销大
  • 适用：复杂微服务

💻 配置示例

# Nginx配置示例
upstream llm_inference {
    # 最少连接策略
    least_conn;

    # 服务器列表和权重
    server 192.168.1.10:8000 weight=3;
    server 192.168.1.11:8000 weight=2;
    server 192.168.1.12:8000 weight=1;

    # 健康检查
    keepalive 32;
}

server {
    listen 80;
    server_name llm.example.com;

    location / {
        proxy_pass http://llm_inference;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Connection "";

        # 超时配置（考虑LLM长推理）
        proxy_connect_timeout 300s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;
    }
}

# HAProxy配置示例
defaults
    mode http
    timeout connect 300s
    timeout client 300s
    timeout server 300s

backend llm_backend

    server server2 192.168.1.11:8000 check weight 2
    server server3 192.168.1.12:8000 check weight 1

frontend llm_frontend
    bind *:80
    default_backend llm_backend

# 自定义负载均衡（Python示例）
from fastapi import FastAPI, HTTPException
from typing import List
import httpx
import torch

app = FastAPI()

class GPULoadBalancer:
    """
    基于GPU状态的负载均衡器
    """
    def __init__(self, servers: List[str]):
        self.servers = servers
        self.gpu_utilization = {server: 0 for server in servers}

    async def get_server(self) -> str:
        """
        获取负载最低的服务器
        """
        # 获取各服务器GPU利用率
        for server in self.servers:
            try:
                async with httpx.AsyncClient() as client:
                    response = await client.get(
                        f"http://{server}/metrics"
                    )
                    metrics = response.json()
                    self.gpu_utilization[server] = metrics.get("gpu_utilization", 0)
            except:
                self.gpu_utilization[server] = 100  # 失败标记

        # 选择GPU利用率最低的服务器
        return min(self.gpu_utilization, key=self.gpu_utilization.get)

# 使用负载均衡器
load_balancer = GPULoadBalancer([
    "192.168.1.10:8000",
    "192.168.1.11:8000",
    "192.168.1.12:8000",
])

@app.post("/generate")
async def generate(request: dict):
    """
    路由到最空闲的服务器
    """
    server = await load_balancer.get_server()

    try:
        async with httpx.AsyncClient() as client:
            response = await client.post(
                f"http://{server}/generate",
                json=request,
                timeout=300.0
            )
            return response.json()
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

@app.get("/health")
async def health():
    return {"status": "healthy"}

📊 负载均衡策略对比

策略 公平性 响应时间 复杂度 适用场景
轮询 高 中 低 通用场景
加权轮询 中 中 低 不同配置服务器
最少连接 高 低 中 长连接场景
最短响应 中 最低 高 实时性要求高
GPU感知 中 低 高 AI推理专用
💡
负载均衡实践建议
  • 优先使用最少连接策略
  • 设置合理的超时时间（考虑LLM长推理）
  • 配置健康检查自动摘除故障节点
  • 监控各节点负载，定期调整权重
  • AI推理服务可考虑GPU感知的负载均衡
