86.4 代码合并策略

Git 合并与变基详解

🎯 学习目标

  • 理解 merge 和 rebase 的区别
  • 掌握三种合并方式的应用场景
  • 学会解决合并冲突
  • 了解最佳实践和注意事项

📚 合并方式对比

# Git 支持三种合并方式 1. Merge Commit (--no-ff) - 创建合并提交 - 保留完整分支历史 - 历史呈分叉状 2. Fast-forward (--ff) - 不创建合并提交 - 线性历史 - 不保留分支信息 3. Rebase - 变基重写历史 - 线性历史 - 更干净但需谨慎使用 # 可视化对比 ## Merge Commit A---B---C feature / \ D---E---F---G---H main (G 是合并提交) ## Fast-forward A---B---C feature \ D---E---F---A---B---C main (直接移动指针) ## Rebase A---B---C feature / D---E---F main # rebase 后 D---E---F---A'---B'---C' main (线性历史)

🔧 Merge Commit 详解

# 创建合并提交 git checkout main git merge --no-ff feature/login # 何时使用 ✅ 合并功能分支到主分支 ✅ 需要保留分支历史 ✅ 团队协作时保留上下文 # 优点 - 保留完整的分支历史 - 清晰看到功能开发时间线 - 安全，不会丢失提交 - 便于回滚整个功能 # 缺点 - 历史图比较复杂 - 提交历史呈分叉状 # GitHub 默认行为 在 GitHub 上合并 PR 时，可以选择： - Create a merge commit (默认) - Squash and merge - Rebase and merge
💡
推荐做法

合并到 main/develop 分支时建议使用 --no-ff，这样可以在历史中清晰地看到每个功能的边界。

⚙️ Rebase 详解

# 变基操作 git checkout feature/login git rebase main # 解决冲突后继续 git add . git rebase --continue # 放弃变基 git rebase --abort # 何时使用 ✅ 同步主分支最新代码到功能分支 ✅ 清理本地提交历史 ✅ 保持提交历史线性 # 优点 - 提交历史更清晰线性 - 避免不必要的合并提交 - 便于 bisect 定位问题 # 缺点 - 重写历史，可能造成问题 - 不适合已推送的分支 - 解决冲突可能更复杂 # 黄金规则 ⚠️ 永远不要对已推送到远程的分支进行 rebase！

🚀 解决合并冲突

# 冲突发生时的文件状态 <<<<<<< HEAD 当前分支的内容 ======= 要合并分支的内容 >>>>>>> feature/login # 解决冲突步骤 ## 1. 查看冲突文件 git status ## 2. 编辑冲突文件 # 选择保留的内容，删除标记符号 ## 3. 标记冲突已解决 git add <conflicted-file> ## 4. 完成合并 # 对于 merge git commit # 对于 rebase git rebase --continue # 使用工具解决冲突 # VS Code 内置冲突解决工具 # 或使用 git mergetool git mergetool

📝 最佳实践

# 合并策略选择指南 ## 1. 功能分支合并到 main/develop 使用 merge commit (--no-ff) 保留功能开发历史 ## 2. 同步主分支更新到功能分支 使用 rebase 保持功能分支历史整洁 ## 3. Pull Request 合并 根据团队规范选择： - 有严格代码审查：merge commit - 追求简洁历史：squash and merge ## 4. 本地临时分支 可以使用 fast-forward 简洁高效 # 注意事项 1. 已推送的分支不要 rebase 2. 合并前先拉取最新代码 3. 冲突解决要仔细检查 4. 重要分支设置保护规则
⚠️
重要提醒

rebase 会重写历史，只应在本地未推送的分支上使用。如果分支已经推送到远程并有人基于它开发，rebase 会造成严重问题。

📝 本节小结

✅
  • • merge commit 保留分支历史，适合合并到主分支
  • • rebase 保持历史线性，适合本地分支整理
  • • 已推送的分支不要 rebase
  • • 解决冲突时要仔细检查代码逻辑
