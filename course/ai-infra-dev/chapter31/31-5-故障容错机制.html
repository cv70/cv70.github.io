故障容错概述

千卡级集群上运行数周的训练任务，面临各种故障风险。完善的容错机制确保系统能够自动检测故障、快速恢复服务、最小化训练损失，保障大模型训练的可靠性和连续性。

🔧 故障分类与特点

硬件故障

  • GPU XID错误、显存ECC错误
  • CPU单核故障、CPU过热
  • 内存错误、DIMM故障
  • 网络设备故障、光模块失效
  • 电源故障、磁盘故障

软件故障

  • OOM（内存溢出）
  • NCCL通信超时、集合通信失败
  • 进程崩溃、段错误
  • 文件系统错误、I/O超时
  • 调度失败、资源不足

🛡️ PyTorch Distributed容错

弹性训练实现

import torch.distributed.elastic as elastic
from torch.distributed.elastic.multiprocessing.errors import record

@record
def main():
    # 初始化分布式环境
    dist.init_process_group(
        backend='nccl',
        init_method='env://'
    )

    # 设置弹性配置
    elastic.rendezvous.RendezvousHandler(
        min_nodes=256,
        max_nodes=256,
        timeout=600
    )

    # 训练循环
    while should_train:
        try:
            data = next(dataloader)
            train_step(data)

            # 定期checkpoint
            if step % checkpoint_interval == 0:
                save_checkpoint()

        except RuntimeError as e:
            # 处理分布式错误
            if is_distributed_error(e):
                log_error(e)
                dist.barrier()
                raise
            else:
                # 其他错误，尝试恢复
                recover_and_retry()

if __name__ == "__main__":
    # 使用elastic launcher
    elastic.launch(
        main,
        nnodes="256",
        nproc_per_node=8,
        max_restarts=3,
    )

PyTorch Distributed提供弹性训练能力，支持节点动态加入和退出，自动处理部分节点故障，确保训练任务的连续性。

🔄 自动恢复策略

故障类型 检测方式 恢复策略 恢复时间
单GPU故障 DCGM监控 重新分配rank，从checkpoint恢复 5-10分钟
单节点故障 心跳超时 重新分配节点，从checkpoint恢复 10-20分钟
网络故障 NCCL超时 重试或重新路由网络 1-5分钟
存储故障 I/O错误 切换到备用存储路径 5-10分钟
OOM错误 系统日志 调整内存配置，重新启动 10-15分钟
多节点故障 告警聚合 暂停训练，人工介入 手动处理
💡
恢复时间目标（RTO）

对于大模型训练，建议设定RTO < 15分钟。通过自动故障检测、快速资源分配、checkpoint预热等手段，将故障恢复时间控制在可接受范围内。

🏥 节点健康检查

自动化健康检查脚本

#!/bin/bash
# 节点健康检查脚本

check_gpu() {
    # 检查GPU状态
    nvidia-smi --query-gpu=health,temperature.gpu,utilization.gpu \
        --format=csv,noheader | while IFS=, read -r health temp util; do
        if [ "$health" != "Ok" ]; then
            echo "GPU unhealthy: $health"
            return 1
        fi
        if [ "$temp" -gt 85 ]; then
            echo "GPU temperature too high: $temp"
            return 1
        fi
    done
    return 0
}

check_network() {
    # 检查网络连接
    ibstat | grep -q "LinkUp" || return 1
    ping -c 1 storage-node >/dev/null || return 1
    return 0
}

check_storage() {
    # 检查存储挂载
    mount | grep -q "/data" || return 1
    df /data | grep -q "/data" || return 1
    return 0
}

# 主检查流程
main() {
    if check_gpu && check_network && check_storage; then
        echo "Node healthy"
        exit 0
    else
        echo "Node unhealthy"
        exit 1
    fi
}

main

⚠️
容错设计原则

快速失败：故障快速暴露，避免雪崩效应。自动恢复：常见故障自动处理，减少人工介入。人工介入：复杂故障提供清晰的诊断信息和操作指引。持续改进：从故障中学习，不断优化容错机制。

🚨 应急响应流程

故障响应SOP

严重故障响应流程：
1. 告警触发
   ├─ 接收告警通知
   ├─ 确认告警级别
   └─ 通知相关人员

2. 故障诊断
   ├─ 检查监控仪表盘
   ├─ 查看系统日志
   ├─ 确定故障范围
   └─ 评估影响程度

3. 应急处理
   ├─ 立即止损（暂停训练）
   ├─ 隔离故障节点
   ├─ 评估恢复方案
   └─ 执行恢复操作

4. 恢复验证
   ├─ 验证节点健康状态
   ├─ 从checkpoint恢复训练
   ├─ 监控恢复后运行状态
   └─ 确认训练正常继续

5. 复盘总结
   ├─ 记录故障详情
   ├─ 分析根本原因
   ├─ 制定改进措施
   └─ 更新容错策略
