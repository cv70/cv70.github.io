基于角色的访问控制实践

RBAC概述

基于角色的访问控制（Role-Based Access Control，RBAC）是一种通过将权限分配给角色， 再将角色分配给用户的权限管理方式。这种方式大大简化了权限管理，提高了安全性和可维护性。

🔄 RBAC核心模型

👤

用户（User）

系统的使用者，可以是人员或服务账户

🎭

角色（Role）

权限的集合，代表某种职责或功能

🔑

权限（Permission）

对资源执行操作的能力

📊 RBAC层次结构

用户
  ↓ 赋予
角色
  ↓ 包含
权限
  ↓ 作用于
资源

角色可以继承其他角色的权限，形成层次结构。

🏢 AI基础设施中的角色设计

角色 职责 典型权限
超级管理员 系统全面管理 所有资源的完全访问权限
集群管理员 计算集群管理 创建/删除节点、配置网络、管理存储
研究员 模型训练开发 提交训练任务、查看日志、使用GPU
数据工程师 数据管理与处理 访问数据集、管理数据流水线
模型工程师 模型部署与优化 部署模型、配置推理服务、监控性能
只读用户 监控与查看 查看资源状态、监控指标、日志

🔄 RBAC vs ABAC

RBAC

  • 基于预定义角色
  • 实现简单，易于理解
  • 适合静态权限需求
  • 权限变更需要角色调整

ABAC

  • 基于属性和策略
  • 更灵活但复杂度高
  • 适合动态权限需求
  • 支持细粒度控制
💡
混合权限模型

在大型AI基础设施中，通常采用RBAC+ABAC的混合模型： 使用RBAC进行粗粒度权限控制，使用ABAC进行细粒度决策。

💻 代码示例：RBAC实现

# RBAC权限检查实现示例
class RBACSystem:
    def __init__(self):
        self.users = {}      # 用户到角色的映射
        self.roles = {}      # 角色到权限的映射
        self.resources = {}  # 资源定义

    def add_user(self, user_id):
        self.users[user_id] = []

    def assign_role(self, user_id, role_id):
        if user_id in self.users and role_id in self.roles:
            self.users[user_id].append(role_id)

    def check_permission(self, user_id, resource, action):
        # 获取用户的所有角色
        roles = self.users.get(user_id, [])

        # 检查任一角色是否有权限
        for role_id in roles:
            permissions = self.roles.get(role_id, [])
            if (resource, action) in permissions:
                return True
        return False

# 使用示例
rbac = RBACSystem()
rbac.roles['researcher'] = [('gpu', 'use'), ('dataset', 'read')]
rbac.users['user001'] = ['researcher']

# 检查权限
if rbac.check_permission('user001', 'gpu', 'use'):
    print("允许使用GPU")

RoleBinding

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: researcher-binding
  namespace: ai-training
subjects:
- kind: User
  name: researcher@company.com
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: researcher
  apiGroup: rbac.authorization.k8s.io

🛡️ 权限管理最佳实践

设计原则

  • 最小权限原则
  • 职责分离
  • 定期权限审计
  • 权限过期机制

实施要点

  • 明确角色定义
  • 建立审批流程
  • 记录权限变更
  • 定期审查权限
⚠️
常见陷阱
  • 角色过多导致管理复杂
  • 权限累积导致过度授权
  • 缺少定期权限审查
  • 服务账户权限过大
