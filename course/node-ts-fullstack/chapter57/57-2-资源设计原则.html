57.2 资源设计原则

设计清晰、一致的 API 资源结构

🎯 资源命名原则

良好的资源命名是 RESTful API 设计的基础。遵循一致的命名规范可以让 API 更易于理解和使用。

核心原则

使用名词而非动词

资源应该是名词，表示实体而非动作。动作由 HTTP 方法表达。

// 好的设计 ✓ GET /users // 获取用户列表 POST /users // 创建用户 GET /users/123 // 获取指定用户 // 不好的设计 ✗ GET /getUsers POST /createUser GET /getUserById/123

使用复数形式

资源名称使用复数形式，表示资源集合，保持 API 的一致性。

// 好的设计 ✓ /users // 用户集合 /articles // 文章集合 /orders // 订单集合 // 不好的设计 ✗ /user /article /order

使用小写字母

URL 中使用小写字母，用连字符分隔单词，提高可读性。

// 好的设计 ✓ /user-profiles /order-items /blog-posts // 不好的设计 ✗ /UserProfiles /orderItems /blogPosts

避免层级过深

资源嵌套层级不宜过深，建议不超过 2-3 层。

// 好的设计 ✓ /users/123/orders /articles/456/comments // 不好的设计 ✗ /users/123/orders/456/items/789

📂 资源类型与设计

1. 集合资源（Collection）

集合资源表示一组同类资源的容器。

// 获取用户列表 GET /users // 创建新用户 POST /users { "name": "张三", "email": "zhangsan@example.com" } // 响应 { "data": [ { "id": 1, "name": "张三" }, { "id": 2, "name": "李四" } ], "total": 2, "page": 1, "pageSize": 10 }

2. 单一资源（Singleton）

单一资源表示特定的实体实例。

// 获取指定用户 GET /users/123 // 更新用户 PUT /users/123 { "name": "张三更新" } // 删除用户 DELETE /users/123 // 部分更新 PATCH /users/123 { "email": "newemail@example.com" }

3. 子资源（Sub-resource）

表示属于某个资源的子级资源。

// 获取用户的所有订单 GET /users/123/orders // 获取用户的特定订单 GET /users/123/orders/456 // 为用户创建订单 POST /users/123/orders { "productId": 789, "quantity": 2 } // 获取文章的所有评论 GET /articles/456/comments

4. 虚拟资源（Virtual Resource）

不直接对应数据库实体，表示概念性资源或操作结果。

// 搜索结果 GET /search?q=typescript&type=article // 统计数据 GET /reports/daily-sales // 当前用户信息 GET /me GET /users/me // 配置信息 GET /settings

🔗 资源关系设计

一对多关系

// 用户与文章：一个用户有多篇文章 GET /users/123/articles // 获取用户的所有文章 POST /users/123/articles // 为用户创建文章 // 文章与评论：一篇文章有多条评论 GET /articles/456/comments // 获取文章的所有评论

多对多关系

// 学生与课程：多对多关系 GET /students/123/courses // 获取学生的所有课程 GET /courses/456/students // 获取课程的所有学生 // 通过关联资源 POST /students/123/courses/456 // 学生选课 DELETE /students/123/courses/456 // 学生退课 // 或使用关联资源名称 GET /enrollments?studentId=123&courseId=456

自引用关系

// 分类与子分类 GET /categories/123/children // 获取子分类 GET /categories/123/parent // 获取父分类 // 员工与上级 GET /employees/123/subordinates // 获取下属 GET /employees/123/manager // 获取上级

💻 NestJS 资源设计示例

// articles.controller.ts import { Controller, Get, Post, Param, Body, Query } from '@nestjs/common'; @Controller('articles') export class ArticlesController { // 集合资源：获取文章列表 @Get() async findAll( @Query('page') page: number = 1, @Query('pageSize') pageSize: number = 10, @Query('status') status?: string, ) { return this.articlesService.findAll({ page, pageSize, status }); } // 单一资源：获取指定文章 @Get(':id') async findOne(@Param('id') id: string) { return this.articlesService.findOne(+id); } // 子资源：获取文章评论 @Get(':id/comments') async getComments( @Param('id') id: string, @Query('page') page: number = 1, ) { return this.commentsService.findByArticle(+id, page); } // 子资源：为文章添加评论 @Post(':id/comments') async addComment( @Param('id') id: string, @Body() createCommentDto: CreateCommentDto, ) { return this.commentsService.create(+id, createCommentDto); } }
⚠️
设计陷阱
  • 避免在 URL 中使用动词：/users/123/getProfile
  • 避免使用文件扩展名：/users.json
  • 避免使用 CRUD 术语：/users/create
  • 避免使用不稳定的命名：/v1/users

📊 资源设计最佳实践对比

场景 推荐设计 不推荐设计
获取列表 GET /users GET /getUsers
获取单个 GET /users/123 GET /user?id=123
创建资源 POST /users POST /createUser
更新资源 PUT /users/123 POST /updateUser
删除资源 DELETE /users/123 GET /deleteUser?id=123
搜索资源 GET /search?q=keyword GET /searchUser/keyword
子资源 GET /users/123/orders GET /orders?userId=123

📝 小结

  • 资源命名使用名词复数形式，使用小写字母和连字符
  • 动作通过 HTTP 方法表达，避免在 URL 中包含动词
  • 合理设计资源嵌套，层级不宜过深
  • 清晰定义资源关系：一对多、多对多、自引用
  • 保持 API 设计的一致性和可预测性
